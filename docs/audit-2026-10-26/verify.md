## New or remaining bugs

| ID | Finding | Severity | Evidence / repro | Fix |
|---|---|---|---|---|
| B1 | A stale cancel for an older Stripe subscription overwrites a newer active Stripe subscription | High | stripe-webhook/index.ts:75-77 reads `cur.stripe_sub` but never compares it. Guard only checks app_store/comp. Repro (reasoned): cancel sub A, then subscribe to sub B. A's `customer.subscription.deleted` (or a retry of it) arrives after B is created. getSub(A) returns canceled, and the row becomes `status=canceled, stripe_sub=A`. The person loses Pro while B keeps charging. | Return early when `status==='canceled' && cur?.stripe_sub && cur.stripe_sub!==sub.id && cur.status!=='canceled'`. |
| B2 | After B1 happens, deleting the account doesn't cancel the live subscription | High (chained) | account/index.ts:40 skips the cancel when `status==='canceled'` and only ever cancels the one `stripe_sub` on file. | On delete, list the customer's subscriptions with status active/trialing/past_due and cancel each, whatever the row's status. |
| B3 | The "already canceled" check is too broad | Low | account/index.ts:42 treats any Stripe error whose body contains "cancel" as success. | Check for a 400 with resource_missing or a body that states the subscription is already canceled. |
